# API Review Checklist

这份清单用于评估一个新 API、组件 API、服务 API 或工具函数，是否适合进入 `y2kit` 的公共层。

## 1. 问题定义

先回答：

- 这是共享问题，还是业务问题？
- 这个能力是否真的需要长期维护？
- 它是否已经可以从现有 API 自然扩展得到？

如果答案不清楚，不要急着新增 API。

## 2. 命名

- 名称是否直接表达用途？
- 是否与现有命名风格一致？
- 是否避免了近义词竞争？
- 同一类概念是否沿用已有词汇，如 `value`、`defaultValue`、`onChange`、`disabled`、`loading`、`variant`、`tone`、`sizePreset`？

## 3. 状态模型

对于有状态 API，检查：

- 是否需要受控模式？
- 是否需要非受控模式？
- 默认行为是否清楚？
- 缺失必要配置时是 fail-fast 还是安全回退？
- 是否会出现多处状态源竞争？

## 4. 一致性

- 是否符合现有设计语言？
- 是否与同类组件 / 工具的参数顺序、命名、事件语义一致？
- 是否把 escape hatch 放在次要位置，而不是让用户一上来就手写所有细节？

## 5. 稳定性与兼容性

- 是否会破坏现有公开 API？
- 如果需要演进，能否先增加兼容层？
- 是否需要 deprecate 策略？
- 是否需要迁移文档或 release note？

## 6. UI 组件额外检查

- 颜色是否来自主题系统？
- 文案是否来自 i18n？
- 是否定义了禁用态、加载态、错误态、空态？
- 是否具备 `accessibilityRole`、必要的 `accessibilityState`？
- 是否具备 `testID` 或等价测试入口？
- 默认交互是否符合用户朴素直觉？

## 7. 性能检查

- 这个 API 是否会诱导业务侧写出高成本用法？
- 高频交互是否避免了不必要重渲染？
- 是否引入了多余对象分配、无意义副作用或热路径计算？
- 优化方式是否建立在正确性和可维护性之上？

## 8. 包边界

- 它为什么属于 `packages/ui` 或 `packages/tools`？
- 是否夹带了业务语义？
- 是否把公共层变成了业务杂物间？

## 9. 文档与发布

- 是否在公共入口导出？
- 是否更新 README / 文档 / 示例？
- 是否需要 changeset？
- 是否需要补充破坏性变更说明？

## 10. 最终判断

一个 API 适合并入公共层，至少应满足：

- 问题真实存在且可复用
- 命名与状态模型清楚
- 与现有 API 语言一致
- 性能、兼容性、稳定性都可自圆其说
- 文档和版本策略跟得上
