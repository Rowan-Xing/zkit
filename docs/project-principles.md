# y2kit 项目原则

这份文档只回答一件事：`y2kit` 的代码应该长成什么样。

## 1. 北极星

`y2kit` 不是靠“功能多”取胜，而是靠下面几件事：

- 稳定：iOS / Android 行为尽量一致，不轻易崩、不轻易抖、不轻易出边界错
- 高性能：高频交互与动画优先走低抖动路径，避免无意义重渲染
- 统一：API 命名、状态模型、导出方式、组件语言统一
- 现代：默认体验简洁、克制、清晰，不堆历史包袱
- 可演进：架构边界明确，新增能力不会迅速把仓库拖乱

## 2. 架构原则

### 2.1 包边界必须稳定

- `packages/ui` 只放共享 UI、主题系统、组件服务和必要内部辅助
- `packages/tools` 只放非 UI 的共享工具
- `apps/example` 只负责演示与联调，不是公共逻辑来源

如果一个能力带明显业务语义，就不该进入公共层。

### 2.2 公共 API 是长期契约

- 公开导出一旦发布，就按长期契约对待
- 演进优先兼容，不优先“重写得更漂亮”
- 需要升级时，先考虑兼容层、弃用期、迁移路径

## 3. API 设计语言

### 3.1 命名统一

同一类概念必须同名，不制造近义词竞争。

优先使用这类语义字段：

- `value` / `defaultValue`
- `checked` / `defaultChecked`
- `open` / `defaultOpen`
- `onChange`
- `disabled`
- `loading`
- `variant`
- `tone`
- `size` 或 `sizePreset`

### 3.2 状态模型统一

有内部状态的组件，优先同时支持：

- 受控模式
- 非受控模式

状态来源必须单一，不做“半受控半非受控”的模糊设计。

### 3.3 先语义，后细节覆盖

- 先提供语义化 API
- 再提供必要的 escape hatch
- 不让样式碎片化配置反客为主

## 4. 性能原则

### 4.1 热路径优先级最高

高频交互组件必须优先考虑：

- 避免不必要重渲染
- 避免热路径临时对象和无意义计算
- 动画与手势优先使用低抖动实现
- Android 体验不能作为次要目标

### 4.2 性能优化必须可解释

- 不做玄学优化
- 不为了跑分牺牲可维护性
- 优化前先确认瓶颈，优化后能说明收益来自哪里

## 5. 稳定性原则

- 默认行为必须可预测
- 边界条件必须明确处理
- 配置缺失时，要么 fail-fast，要么有清楚兜底，不要沉默错乱
- 平台差异必须显式处理，不能把 Android / iOS 差异留给业务踩坑
- 依赖引入要克制，尤其是热路径和原生依赖

## 6. 现代化的定义

这里的“现代化”不是复杂，而是：

- 默认视觉清楚
- 状态反馈自然
- API 足够语义化
- 代码结构简洁
- 旧包袱逐步收敛，而不是继续扩散

## 7. 每次新增能力前先问

1. 这是共享能力还是业务能力？
2. 它的 API 是否符合现有语言？
3. 它会不会带来新的维护负担？
4. 它在 Android / iOS 上是否都成立？
5. 它会不会让热路径变重？

如果这些问题说不清，就不要急着并入公共层。
