# y2kit 项目原则

## 1. 项目目标

`y2kit` 要做的不是“再造一个能跑的组件库”。

它要成为一套可以长期公开维护、可被真实业务反复复用、升级成本可控、体验与实现同样稳定的 React Native 基础设施。

顶级开源项目的标准，不只是功能多，而是：

- 用户拿来就能理解，默认行为符合直觉
- 开发者接入成本低，排查成本低，升级预期稳定
- API 有统一语言，不会出现“每个组件一套习惯”
- 改动有边界，发布有纪律，文档永远跟得上实现
- 性能优化建立在正确性、稳定性、兼容性之上，而不是相反

## 2. 决策原则

### 2.1 硬约束

以下不是“加分项”，而是硬约束：

- 正确性：组件行为、状态流转、边界条件必须正确
- 稳定性：公开 API 与默认行为必须可预期
- 兼容性：真实 App 的接入方式、平台差异、升级路径必须被考虑
- 可维护性：结构、命名、边界、文档必须支持长期演进

### 2.2 在硬约束内追求极致性能

性能很重要，但方式必须正确：

- 热路径优先减少不必要重渲染与临时对象分配
- 高频交互动效优先放到 UI 线程或等价低抖动路径
- 优化要可解释、可验证，避免“玄学优化”
- 不为了跑分牺牲 API 清晰度、调试性或平台稳定性

### 2.3 现代化不是堆特效

现代化意味着：

- 默认视觉克制、清晰、有层次
- 状态切换自然，反馈及时，但不过度干扰
- 主题、暗色、国际化、无障碍是系统能力，不是补丁
- 默认值安全，空态、错态、加载态、禁用态都被认真设计

## 3. 朴素直觉

### 3.1 面向用户的朴素直觉

组件交互应满足：

- 看起来像能点，就真能点；看起来不能点，就必须明确禁用
- 切换、选择、展开、关闭等行为不应制造意外
- 相同模式在不同组件里尽量一致
- 反馈足够快，但不过度跳动、闪烁或打断

### 3.2 面向开发者的朴素直觉

开发体验应满足：

- 同一类概念尽量同名
- 同一类状态尽量同构
- 受控与非受控边界清楚
- 默认值、异常、缺失配置的处理策略清楚
- 看到 API 名称就能大致猜到行为

## 4. API 设计语言

### 4.1 统一命名

- 同一概念保持同一命名，不制造近义词竞争
- 状态型组件优先明确主状态字段与变化回调的对应关系
- 语义命名优先于视觉命名，例如优先 `variant`、`tone`、`size`，而不是语义不清的自定义缩写

### 4.2 受控 / 非受控明确

组件如果有内部状态，优先显式支持：

- 受控：`value/checked/open/...` + 对应回调
- 非受控：`defaultValue/defaultChecked/defaultOpen/...`

不要制造混合状态来源，避免“看起来可控，实际半可控”。

### 4.3 先语义，后逃生口

- 先给语义化 props，让大部分业务无需手写样式即可得到一致结果
- 再提供 `style`、`contentStyle`、`textStyle` 这类 escape hatch
- escape hatch 必须存在，但不能反客为主，破坏统一设计语言

### 4.4 向后兼容优先

- 已发布 API 视为契约
- 需要演进时，优先增加兼容层与弃用提示，而不是直接替换
- 破坏性变化必须附带迁移说明、版本策略和变更理由

## 5. 视觉与系统能力

共享 UI 默认要求：

- 颜色来自主题系统，而不是散落的硬编码品牌色
- 文案走 i18n 通道，而不是写死在组件内部
- 交互组件具备 `accessibilityRole`、必要的 `accessibilityState`
- 需要自动化验证的组件应支持 `testID` 或等价透传
- 暗色模式、禁用态、加载态、错误态应有一致策略

## 6. 包边界

- `packages/ui` 只放共享 UI、主题、i18n、服务组件、调试工具及其轻量内部辅助
- `packages/tools` 只放与 UI 无强耦合、可复用的通用工具
- `apps/example` 只做演示与联调，不承载公共逻辑的真实来源

详细边界见 `docs/package-boundaries.md`。

## 7. 开源质量标准

一个功能只有在同时满足以下条件时，才算真正完成：

- 代码结构清楚，边界正确
- 公开导出合理，类型完整
- 文档同步更新
- 示例可帮助理解，不靠猜
- 变更对旧用户是否兼容有明确说明
- 构建与类型检查可通过

## 8. 对未来改动的要求

新增能力时，优先问这几个问题：

1. 这是共享问题，还是业务问题？
2. 这个 API 是否符合现有语言，而不是另起一套？
3. 它是否会增加未来的维护负担？
4. 它在低端设备、弱网、深色模式、无障碍场景下是否仍然成立？
5. 它的默认行为是否足够直觉？

如果这些问题回答不清楚，就不要急着把能力并入公共包。
